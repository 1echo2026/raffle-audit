> 本文所有口径均与 `assets/audit-core.js` 的 `audit()` 主流程逐条对应，标注了代码位置（函数名 / 注释编号），复刻时按本文实现即可对齐结果。UI 层的人工裁决在 `assets/app.js` 的 `applyOverrides()`。

| 参数 | 页面控件 | 默认值 | 说明 |

## 3. 两套订单池口径（最容易混淆，务必区分）

| | 匹配池 | 有效订单池 |
| --- | --- | --- |
| 渠道 | **全部渠道**（只要求 ≥999、时间合规） | 仅渠道前缀以 `grow_xcg_zhuanjs_xiaoshou` 开头 |
| 变量 | `allRows` | `validRows` |
| 用途 | 加密手机号查订单、判断"订单是否存在"、渠道异常归类 | 工号累计判池、有效出单统计、有效订单池导出 |
| 设计意图 | 渠道差异不导致"查无此单"，而是在资格判定阶段归类为渠道异常 | 只有销售直推出单才计入业绩与门槛 |

**订单去重**（在拆池之后、判池之前）：键 = `订单ID + '|' + 商品ID`，同键只保留第一条，防止同一订单在强基 / 升学两池重复导出与重复累计。商品 ID 列缺失时按空串参与拼键。

过滤统计 `stats`：`total`（过滤前行数）、`rejAmount`（金额不足剔除）、`rejTime`（时间不符剔除）、`noPhone`（手机号空/0/格式错，保留但不可匹配）、`kept`（进入匹配池的行数）。

## 4. 工号累计与逐单判池（核心口径）

只对**有效订单池**（销售直推）执行，代码在 audit() 第 3 步：

1. 按 `订单ID` 聚合金额（同一订单多行时金额相加），记录工号、支付时间、加密手机号、账号；
2. 每个工号的订单按支付时间升序排列（时间为空排最后），逐单维护累计金额 `cum`：
   - **单笔金额 ≥ 2 万**：该单 `direct_peak=true`，直接判巅峰；
   - 否则看累计：**累计后 ≥ 2 万的那一笔及之后所有单**判巅峰；之前的单判进阶；
3. 记录 `peak_since`（首次达到巅峰的时间）、`peak_orders`（巅峰单数）、`max_single`（最大单笔）、`total`（工号累计有效金额）、`row_count`（有效订单行数）；
4. 同一工号多个出单手机号**合并累计**（累计键是工号，不是手机号）；
5. 工号对应的销售姓名按订单行出现次数"多数投票"得出（`ghStats.sales_name`）。

问卷行的**期望奖池 `expected_pool`**：取该手机号关联的全部有效订单，只要其中任一单在工号时间线里被判巅峰 → 期望巅峰，否则期望进阶。同时生成人话版 `peak_reason`（单笔达标 / 累计达标 / 未满 2 万三种文案，含金额与时间）。

## 5. 加密手机号匹配与掩码撞号二次匹配

### 5.1 掩码规则

- 问卷手机号用正则 `1\d{10}` 提取 11 位；提取不到 → `phone_format_ok=false`，最终归「手机号格式不正确」；
- 掩码 `maskPhone(p)` = 前 3 位 + `****` + 后 4 位（长度 < 7 时原样返回）；订单池里全号与掩码号都按此形式入索引。

### 5.2 匹配分支（audit() 第 5 步）

1. **查无订单**：掩码在匹配池索引中不存在 → 资格判定阶段给「手机号在订单池中查找不到，疑似输入错误」；
2. **命中单一账号**：候选订单全部属于同一 `账号ID` → `match='ok'`，直接通过归属；
3. **命中多个账号（前 3 后 4 撞号）**：
   - 取问卷「销售姓名」（`form_sales`，归一化去空格转小写）与候选订单的 **销售姓名 / ccid** 精确匹配；
   - 唯一命中一个账号 → 通过，备注「手机号掩码撞号，按销售姓名二次匹配唯一命中，ccid=xxx」（`remark_note`）；
   - 问卷没填销售姓名（hit=none）、匹配 0 条（zero）、仍命中多账号（multi）→ 挂 `collision` 转待审核，无效原因列出全部候选（姓名 / ccid / 账号 / 工号）。

### 5.3 匹配通过后的取值口径

- 销售姓名、工号：在该手机号的有效订单行中按出现次数多数投票（忽略空值）；
- 转化金额 `convert_amount`：该手机号匹配到的有效订单金额合计；
- 出单时间 `order_time`：取「业绩归属时间」列最大值；该列缺失时回退支付时间；
- 工号为空：置 `gonghao_missing=true` 便于人工核查；
- 订单状态含「完全退款 / 换课原订单」：拼到 `abnormal_status`，有效行也会进沟通话术表并在备注提示核查。

## 6. 渠道异常分类

匹配到订单、但这些订单**全部不是销售直推渠道**时（`xsRows` 为空），置 `channel_bad` 并提前返回（不做工号判池）。资格判定时按渠道码（去掉 `&&null&&null` 脏后缀）分两类：

| 渠道前缀 | 归类异常类型 | 无效原因关键词 |
| --- | --- | --- |
| `grow_xcg_zhuanjs_fudao` 开头 | 非销售直推（辅导 leads 接单） | 「属于辅导leads接单」 |
| 其它非销售渠道 | 非转介绍 | 「不属于转介绍出单」 |

## 7. 去重规则（一个手机号只保留一次抽奖）

仅对 `phone_format_ok=true` 的行按手机号分组，组内 >1 条时：

1. 按问卷**提交时间升序**，保留最早一条；提交时间无法解析的排最后；
2. **同时刻并列**（进阶全量表单与巅峰表单出现完全相同提交）：优先保留**巅峰**那条，避免巅峰提交被进阶副本误剔；
3. **应属巅峰的跨池保留**：若被保留行的 `expected_pool='巅峰'`，则在组内改保留巅峰奖池那条（覆盖"先抽进阶、后续累计达标"的情形）；
4. 其余行置 `is_duplicate=true`，记录 `dup_kept`（保留行的奖品/姓名/提交时间）供页面对照；重复行不进有效/无效名单，单独在「重复剔除」区域与沟通话术表展示。

## 8. 资格判定与无效原因全量清单

每条问卷行收集 `reasons[]`，**有任一原因 → 无效名单；无原因 → 有效名单**。重复行在判定后直接 return，不重复计数。判定顺序：

| 序 | 条件 | 无效原因文案（界面原样） | 异常类型 |
| --- | --- | --- | --- |
| 0 | 手机号栏、真实姓名或昵称中命中绿色通道码 | 无（直接放行，见第 10 节） | — |
| 1 | 提交时间超出问卷时间范围 | 问卷提交时间 X 不在本期活动时间范围内 | 提交时间超范围 |
| 2 | 手机号提取失败 | 出单手机号格式不正确，在订单池中查找不到，疑似输入错误 | 手机号格式错误 |
| 3a | `channel_bad` 且辅导渠道 | 未在有效订单池查找到（…非销售直推渠道：X，属于辅导leads接单） | 非销售直推 |
| 3b | `channel_bad` 其它渠道 | 未在有效订单池查找到（…非转介绍渠道：X，不属于转介绍出单） | 非转介绍 |
| 4a | 原始订单池能查到、但支付时间全部超范围 | 出单时间不符合当前抽奖日期（…不在本期活动时间范围内） | 出单时间不符合当前抽奖日期 |
| 4b | 撞号无法唯一归属 | 加密手机号掩码撞号（…共 N 个账号…）+ 候选清单 | 手机号掩码撞号 |
| 4c | 多账号达标但无撞号结构 | 未在有效订单池查找到（…匹配到多个账号的达标订单，无法唯一归属） | 手机号掩码撞号 |
| 4d | 原始池有单但均不足 999 | 未在有效订单池查找到（订单金额不足 999 元，未达活动有效条件） | 订单未达有效条件 |
| 4e | 原始池完全查不到 | 手机号在订单池中查找不到，疑似输入错误 | 手机号未查到 |
| 5 | 头像校验失败（仅发放表流程） | 问卷头像与中奖名单无法匹配 | 头像无法匹配 |
| 6 | 实际抽奖池 ≠ 期望奖池 | `peak_reason` 全文 + 「但本次在 X 奖池抽奖」 | 抽错奖池（应属巅峰 / 应属进阶） |
| — | 重复行 | 不进无效名单，单列重复剔除 | 重复抽奖 |
| — | 兜底 | 以上都不匹配且有异常状态 | 含退款/换课订单 / 其他异常 |

异常类型由 `classifyAbnormal(s)` 按无效原因关键词映射，用于沟通话术页筛选与模板匹配。

## 9. 宠粉数据总结（summary）口径

导出子表「宠粉数据总结」左右两栏：左红=巅峰奖池（单笔 ≥ 2 万的订单区间），右绿=进阶奖池（999 ≤ 单笔 < 2 万区间）。**统计对象是订单，不是问卷**（`orderAgg` 聚合后的订单）。

| 导出行 | 字段 | 计算口径 |
| --- | --- | --- |
| 出单数 | `orders` | 该金额区间内、加密手机号格式有效的**去重手机号数** |
| 出单人数 | `people` | 该区间内有出单的**去重工号数**（人数口径 = 工号数） |
| 参与人次 | `times` | 该奖池问卷中填了手机号的提交条数（含无效、含重复） |
| 参与人数 | `participants` | 该奖池问卷中出现过的去重工号数 |
| 实际参与人次 | `actual` | 该奖池中 `match='ok'` 且 `expected_pool` 等于本池的去重手机号数 |
| 人数参与率 | `peopleRate` | 参与人数 ÷ 出单人数（分母为 0 记 0） |
| 人次参与率 | `timesRate` | 实际参与人次 ÷ 参与人数（分母为 0 记 0） |

> 旧历史存档无 `summary` 时，`app.js → summaryFallback()` 用导出的有效订单池行按相同区间口径兜底重算，保证老存档也能导出该子表。

## 10. 绿色通道码

- **首页生成**：`genGreenCode()` 生成 8 位随机码（字符集剔除易混的 0/1/I/L/O），存 `raffle_green_codes_v1`；
- **行内「✅ 通过」**：`greenPass()` 自动生成 `GC+时间戳` 凭证码，无需人工复制；
- **判定时机**：audit() 资格判定第 0 步，按以下顺序识别，命中即跳过全部匹配与时间检查，直接入有效名单（重复行除外）：
  1. 问卷「出单手机号/ID」栏文本；
  2. 「真实姓名」或「用户昵称」中的备注（如 `张三 8K3D92AB`、`张三(8K3D92AB)`、`张三 GREEN-8K3D-92`）；
- **识别方式**（`findGreenCode`）：把文本转为大写并去掉所有非字母数字字符后与绿码集合比对，因此空格、括号、连字符、大小写都不影响；纯数字码要求整串相等，避免手机号中恰好包含数字串被误放行；
- **姓名清理**（`stripGreenCode`）：命中来自姓名字段时，把码连同前后括号与 `GREEN` 前缀一并剥离，`real_name` / `nickname` 只保留干净姓名，导出与获奖名单不受影响；
- 备注区分：手机号栏命中记「绿色通道码放行」，姓名/昵称命中记「姓名备注绿色通道码放行」；
- 绿码不是密码体系，仅本机保存、本期人工放行凭证。

## 11. 人工裁决层（app.js，不进 audit-core）

核心是 `overrides` 对象，键为问卷稳定身份 `form_i`，在每次 `AuditCore.audit()` 之后由 `applyOverrides()` 套用：

| 裁决动作 | 写入的 override 形态 | 效果 |
| --- | --- | --- |
| 无效名单「✅ 通过」 | `{green_code, manual:true}` | 无效 → 有效（重复行也可强行并入），备注「绿色通道通过(码)」 |
| 明细表「✕ fail」 | `{rejected:true, reason}` | 有效 → 无效；若该行原本是通过进来的，退回时保留原无效原因 |
| 「🕓 待审核」 | `{audit:'待审核通过补发'}` | 不改名单归属，沟通话术表「报备审核」列写该文案，同时「无效原因」改写为「待审核通过后补发奖品」（仍可再编辑）；再点一次删除即取消 |
| 「✏️ 修改」 | 写回问卷原始行后整体重跑 | 按列映射把新姓名/手机号/基地写回 `raw_row`，再 `rerunAudit()` 全量重算 |
| 话术表就地编辑 | `commEdits[form_i]` 补丁 | 仅覆盖沟通话术导出，不改审核结果；可编辑 基地/姓名/工号/出单手机号/奖池/奖品/异常类型/异常原因/处理话术/报备审核；「处理话术」列右键可一键复制 |
| 无效名单就地编辑 | 直接改 `s.<字段>` 并同步到 communication | 全数据列可改（奖池/昵称/基地/姓名/手机号/工号/奖品/应属奖池/提交时间/无效原因），改后仅本会话显示与导出生效；改「无效原因」会按关键词重算异常类型 |

持久化与沿用：

- `persistManual()` 把 overrides / commEdits 存 `raffle_last_manual_v1`；
- 文件签名（四个文件名排序拼接，`raffle_last_filesig_v1`）相同时点开始审核 → 弹「沿用上次记录」；
- 沿用时以最近一次人工处理为准恢复，被恢复的行标 `is_carry`（界面淡紫色），并统计本次新增条数；
- 手动「保存当前审核结果」存完整快照到 `raffle_history_v1`（上限 15 条，支持右键命名/置顶/标注）。

## 12. 高经团队周进度核算口径（team-progress.js）

1. **月目标**：同名团队多行累加；保存后锁定在 `raffle_team_goal_v1`；
2. **GMV 聚合**：同名团队转化金额累加、单数 = 明细行数；「合计/总计/小计/汇总」行剔除；
3. **周目标** = 月目标 ÷ 当月天数 × 本期天数（两个天数均可在页面改）；
4. **目标完成度** = 本期转化金额 ÷ 月目标 × 100%；
5. **排序**：完成度降序，第一名整行高亮 + 🏆；未设月目标的团队排最后并标注「未设目标」；
6. 基地列存在时按团队聚合输出基地。

## 14. 复刻时的边界注意事项

1. **时间解析**：`parseDt()` 先按 `yyyy-MM-dd HH:mm[:ss]` 正则构造**本地时间**（避免 `new Date('yyyy-MM-dd')` 的 UTC 时区偏差），失败再回退原生解析；
2. **金额解析**：`toFloat()` 去千分位逗号后 `parseFloat`，非数按 0；
3. **空手机号行保留**：问卷手机号为空的行不丢弃，保证人工修改后记录仍在；
4. **form_i 稳定性**：进阶 = 工作表行号，巅峰 = 1000000 + 行号，所有人工裁决按它锚定，排序/编辑都不漂移；
5. **订单状态提示**不阻断：「完全退款/换课原订单」只加备注，不自动判无效；
6. **组织架构提基地**：按 北京/武汉/成都/西安/合肥/新乡/郑州 关键词从组织架构字符串提取；
7. 页面统计卡数字 = `stats`，与导出子表行数一致；若对不上，先检查是否有人工裁决改变了 valid/invalid 归属。
